# ECHO MINI 固件分析记忆

## 已解决: FUN_0003f862 控制流分析 (2026-02-20)

### 问题根因

1. **CBZ 指令未处理**: Theme 0 通过 `CBZ R0, 0x3F8B2` 跳转，**跳过了 `MOVW R4, #0xFFFF`**
   - 模拟器错误地预设 R4=0xFFFF，但 Theme 0 的 R4 实际未初始化

2. **IT 块解码错误**: `BF04` 被误解码为 1 条指令，实际是 **ITT EQ (2 条指令)**
   - 错误理解 mask 编码：指令数由 **最低位 1 的位置** 决定，而非高位

### ARM IT 指令正确解码 (ARM 官方 Table A6-3)

**Mask 编码规则:**
- mask=1000 (8): 1 条指令 (IT)
- mask=01xx (4,5,6,7): 2 条指令 (ITT 或 ITE)
- mask=001x (2,3): 3 条指令
- mask=0001 (1): 4 条指令

**指令数 = 4 - (最低位 1 的位置)**

**条件解码:**
- 第 1 条：总是 `firstcond`
- 第 i 条 (i>1)：检查 `mask[4-i]`
  - 如果 `mask[4-i] == firstcond[0]` → T → 同条件 (`firstcond`)
  - 如果 `mask[4-i] != firstcond[0]` → E → 反条件 (`firstcond^1`)

**示例 BF04:**
- firstcond=0 (EQ), mask=0100 (4)
- 最低位 1 在 bit 2 → 2 条指令
- 第 2 条: mask[3]=0 == fc[0]=0 → T → EQ
- 结论: **ITT EQ** = 2 条都用 EQ 条件


## 主题色彩提取 (2026-02-20 更新 V2)

### 代码模式类型

检测到的三种主题颜色代码模式:

1. **完整5主题 Switch-Case**
   - CMP #0 + BEQ (跳转到 default case)
   - CMP #1-4 + MOVW + BEQ
   - Theme 0 的颜色在 BEQ 目标位置

2. **ITE 条件执行模式** (如 FLAC String)
   - 16-bit CMP + ITE 指令
   - 两个连续的 MOVW (条件真/假)
   - Theme 4 用一个颜色，其他用另一个

3. **预加载+条件存储模式** (如菜单文字颜色)
   - 函数开头 MOVW 加载多个颜色到寄存器
   - CMP + BEQ 条件分支
   - STRH 存储颜色到 RAM 地址
   - 需要控制流模拟来完整提取

### 关键发现

**跑马灯前景色 ≠ FLAC String 颜色!**

| UI 元素 | 函数 | 地址 | 模式 |
|---------|------|------|------|
| 跑马灯/滚动文本覆盖背景 | FUN_0003cfc4 | 0x3CFEC | switch-case |
| FLAC String 文字 | FUN_00086c3c | 0x86CB0 | ITE |
| 进度条背景 | FUN_00087264 | 0x8728C | switch-case |
| 菜单文字颜色 | FUN_0003f862 | 0x3F874 | 预加载+存储 |

**提取工具**: `theme_color_analyzer_v2.py`
- 纯代码模式分析，无颜色值假设
- 检测三种模式: switch-case, ITE, 预加载+存储
- 支持单色和多色函数

### Switch-Case 模式示例

```
CMP R0, #0           ; if theme == 0
BEQ default_case     ; jump to theme 0 handler
CMP R0, #1
MOVW R0, #0x10A2     ; theme 1 color
BEQ end
...
default_case:        ; theme 0 handler
MOVW R0, #0x632C     ; theme 0 color
```

### 发现的函数 (V3.1.0)
| 地址 | 用途 |
|------|------|
| 0x3CFEC | UI 元素颜色 |
| 0x8728C | 进度条背景 (FUN_00087254) |

### ARM Thumb CMP 解码修正

**错误**: 旧代码计算 `imm12 = (i << 11) | (imm4 << 12) | (imm3 << 8) | imm8`

**正确**: CMP T4 编码中 `imm12 = i:imm3:imm8` (imm4 不参与)
```python
imm12 = (i << 11) | (imm3 << 8) | imm8
```

**为什么是错的**:
1. **无代码证据**: 没有找到 `palette[theme_index][color_index]` 的访问模式

```c
// 地址计算使用 block_index * 0x800，暗示数据是分块的
```

**正确理解**: 数据可能是按 UI 元素/资源分块存储，不是按主题连续存储

## FUN_000705b8 数据加载机制 (2026-02-19 Ghidra 反编译 ⭐⭐⭐)

### 核心发现: 数据是分块加载的，不是连续调色板！

**反编译代码关键部分**:
```c
// FUN_000705b8 @ 0x000705b8

// 1. 从元数据读取参数
iVar7 = *(int *)(DAT_00079de8 + 0x1b);    // 大小
iVar10 = *(ushort *)(DAT_00079de8 + 8)    // 偏移
       + *(int *)(DAT_00079de8 + 0x23);   // + 基地址
cVar1 = *_FUN_00079dec;                   // 模式 (1=16bit, 2=32bit, 3=bitmap)

// 2. 分块加载数据 (关键!)
// 内循环: 加载 4 个 bank，每个 32 字节
uVar8 = 0;
do {
    FUN_00068c62(*DAT_00079df4,                    // 源: 资源指针
                 iVar10 + uVar8 * 0x20,            // 偏移 + bank*32
                 0x20,                              // 大小: 32 字节 (16 色)
                 piRam00079df0 + uVar8 * 0x1000);  // 目标: 调色板RAM + bank*4KB
    uVar8 = uVar8 + 1;
} while (uVar8 < 4);

// 3. 外循环: 步进 128 字节
iVar10 = iVar10 + 0x80;  // 下一组 4 个 chunk
```

### 资源加载机制 (反编译确认 ✅)

**关键**: 资源使用 RAM 结构 + 资源 ID 机制，不是 theme_select 索引

**加载流程**:
```
FUN_000823b6 (主题应用)
    → FUN_0008238c
        → FUN_000705b8(0x3E)  // 加载资源 62
            → 读取 RAM 0x030767DC 结构
            → 使用 RAM 0x0301E560 (调色板 RAM)
            → 调用 FUN_00068c62 加载数据块
```

**RAM 结构 (反编译确认 ✅)**:
| 地址 | 用途 | 代码引用 |
|------|------|----------|
| 0x030767D0 | 设备/模式结构 | FUN_00042aca |
| 0x030767D8 | 资源指针 | FUN_00079d34 |
| 0x030767DC | 资源元数据 | FUN_00079d34, FUN_000705b8 |
| 0x0301E560 | 调色板 RAM | 多个函数 |

**ROM 0x79DE0 指针表** (各函数独立引用，非复制模板):
```
偏移    值            指向 RAM        使用函数
[+0x00] 0x0000B905   (魔数/标志)
```

### 为什么有些 RAM 地址无 ROM 引用? (Rockbox 文档解释)

**来自 Rockbox 的 RKnanoD 内存映射**:
```
地址范围              类型        说明
0x01000000-0x01FFFFFF IRAM       on-chip RAM
0x20000000-0x3FFFFFFF SRAM       on-chip RAM ← 我们的变量在这里
0x22000000-0x24000000 Bit-band   SRAM 位带别名
0x40000000-0x5FFFFFFF Peripherals on-chip 外设
```

**解释**: RAM 地址不会直接出现在 ROM 代码中，除非：
1. **编译器常量池**: 如 DAT_0009a5f0 = 0x0301D140
2. **运行时计算**: `ptr = base + offset`
3. **栈/局部变量**: 函数内的局部变量

**0x0304A4E4 无引用的原因**:
- 这是纯 RAM 地址
- 通过运行时计算访问，而非 ROM 常量
- 可能是: `&struct.field` 或 `local_variable`

```
┌─────────────────────────────────────────────────────────────────────┐
│                    ROM vs RAM 引用区别                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ROM 中有引用 (编译器常量池):                                         │
│  ┌─────────────────┐                                               │
│  │ DAT_0009a5f0    │ = 0x0301D140  ← 共享的结构体基址               │
│  │ DAT_00086d18    │ = 0x0301D140  ← 同一地址的多个副本             │
│  └─────────────────┘                                               │
│                                                                     │
│  ROM 中无引用 (运行时计算):                                          │
│  ┌─────────────────┐                                               │
│  │ 0x0304A4E4      │ = base + 动态偏移                             │
│  │                 │ 或局部变量地址                                 │
│  │                 │ 无法在静态分析中找到                           │
│  └─────────────────┘                                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```
